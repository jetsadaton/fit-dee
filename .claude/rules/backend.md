# Backend Rules

## Tech Stack

TypeScript · Next.js 15 (App Router, Route Handlers) · **Drizzle ORM** · **Neon Postgres** (+ pgvector) · **Zod** validation · **Auth.js v5** (LINE + Google) · **Inngest** (background jobs) · **Vercel AI SDK** + Kimi K2.6 · **In-DB LLM tracing** via `messages` table (Helicone/Langfuse deferred) · **Vercel Blob** (storage) · **Upstash Redis** (rate limit + cache).

## Architecture: Feature-folder + Service/Repository

```
app/
├── (chat)/                # RSC + client islands for chat UI
├── (app)/today/           # RSC dashboard
├── (app)/plan/            # RSC plan + run mode (client island)
├── api/
│   ├── chat/route.ts      # streaming Kimi via Vercel AI SDK
│   ├── food/route.ts      # CRUD food logs
│   ├── auth/[...nextauth] # Auth.js v5
│   ├── inngest/route.ts   # Inngest webhook
│   └── webhooks/line/...  # LINE OA webhook (Phase 4)
lib/
├── ai/
│   ├── kimi.ts            # OpenAI-compatible client + system prompt builder
│   ├── tools/             # tool definitions (one file per tool)
│   ├── memory.ts          # memory blocks (profile + 7d summary + last-20 + notes)
│   └── prompts/           # versioned system prompts (eval-tracked)
├── db/
│   ├── schema.ts          # Drizzle schema (SOURCE OF TRUTH)
│   ├── client.ts          # Neon connection
│   └── repositories/      # one file per aggregate (foods, logs, plans, ...)
├── services/              # business logic (TDEE calc, plan generator, recalibration)
├── auth.ts                # Auth.js config (LINE + Google providers)
└── types/                 # shared types (db/* + dto/*)
inngest/
└── functions/             # weekly insights, plan gen, photo expiry
drizzle/
└── migrations/            # auto-generated by drizzle-kit
```

**Layer responsibilities**:

| Layer                                       | Lives here                                                 | Does NOT                |
| ------------------------------------------- | ---------------------------------------------------------- | ----------------------- |
| **Route Handler** (`app/api/.../route.ts`)  | parse request, auth check, call service, format response   | business logic, raw SQL |
| **Service** (`lib/services/*.ts`)           | business rules (TDEE, macro calc, plan gen, recalibration) | HTTP, SQL               |
| **Repository** (`lib/db/repositories/*.ts`) | DB queries via Drizzle, transactions                       | business rules, HTTP    |
| **AI tool handler** (`lib/ai/tools/*.ts`)   | wrap services into LLM-callable tools w/ Zod schema        | inline DB queries       |

Reference file (จะมีหลัง Phase 0): `app/api/food/route.ts` + `lib/services/food.ts` + `lib/db/repositories/food-logs.ts`

## Data access strategy

| Query shape                                 | Use                                | Why                        |
| ------------------------------------------- | ---------------------------------- | -------------------------- |
| Simple CRUD on aggregate                    | Drizzle query in repository        | type-safe, close to schema |
| Complex aggregation (weekly summary, trend) | Drizzle SQL builder + raw helpers  | composable, still typed    |
| Vector search (food cache)                  | `pgvector` via Drizzle custom type | on-platform                |
| Cross-aggregate read for RSC                | view or denormalized read model    | RSC ต้องเร็ว               |

## Auth / identity

- ใช้ Auth.js v5 — session ผ่าน JWT
- **อ่าน user identity จาก `auth()` ใน Route Handler / Server Action**, ห้ามอ่านจาก request body
- Request schema (Zod) ห้ามมี `userId` / `email` — leak สิทธิ์
- LINE Login = primary; Google = secondary; users table มี `line_sub` + `google_sub` unique columns
- Rate-limit ทุก LLM endpoint ด้วย Upstash Redis (per `user_id`, sliding window)

## Schema verification (data layer)

- **Source of truth = `lib/db/schema.ts` (Drizzle)**
- ก่อนเขียน query ใหม่ → อ่าน schema file ก่อน ห้ามเดาชื่อ column / FK
- เปลี่ยน schema → ต้อง `pnpm db:generate` แล้ว commit migration ใน `drizzle/migrations/`
- `pnpm db:studio` เปิดดู production-like data ได้ (ใช้ Neon branch สำหรับ preview)

## LLM tool rules (specific to Coachly)

- ทุก tool ใน `lib/ai/tools/` ต้อง:
  1. มี Zod schema ที่ tight (enum สำหรับ `meal_type`, `goal`, `activity_level`)
  2. ใช้ semantic ID (`thai_pad_kra_pao_chicken`) ไม่ใช่ UUID
  3. return confirm payload ให้ UI render card ก่อน commit
  4. มี golden test ใน `tests/eval/<tool>.test.ts`
- **ห้าม** สร้าง row ลง `foods` table จาก LLM โดยตรง — LLM ต้องเรียก `search_food()` ก่อน, ถ้าไม่เจอจึงเรียก `create_food_from_estimate()` ที่ flag `source='llm_estimate'`

## Hard rules

- ห้ามแก้ auto-generated: `drizzle/migrations/*.sql`, `*.generated.ts`, `next-env.d.ts`
- ใช้ Drizzle parameterized queries เสมอ — ห้าม template string SQL
- **Postgres-only** features OK (Neon = Postgres 16); ห้ามคิดถึง MySQL/SQLite portability
- Edge runtime สำหรับ read-only routes (ใช้ `@neondatabase/serverless` HTTP); Node runtime สำหรับ AI streaming + Inngest
- ห้าม return raw DB row ออก API — แปลงเป็น DTO ก่อน (ดู `rules/types.md`)
- ห้าม log PII — prompt ที่ส่งไป Kimi ต้องไม่มี email/ชื่อจริง. ใช้ `user_id_hash` (SHA-256 ของ users.id) + numeric profile เท่านั้น. `messages` table ใน DB เก็บ prompt + token + latency ครบ — ถือเป็น source of truth สำหรับ debug AI
